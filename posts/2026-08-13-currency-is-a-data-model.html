Multi-currency is a data-modelling problem, not a formatting problem

Showing a number in a different currency looks like a display concern. It is not. Get it wrong and your history grows a step change through its middle, an FX move vanishes from a chart, and a function you wrote six months ago is still quietly answering in last year's currency.

I have a dashboard that values a portfolio held across several markets. It has a dropdown that switches the display currency, and for about a week that dropdown was the simplest feature in the project: multiply everything by a rate on the way to the screen.

Then I looked at the net-worth chart and found a step change through the middle of it, on a day when nothing had happened.

Currency is not a formatting layer. It is part of the type of the number, and every place a number is written down, read back, compared to another number, or summed is a place where the currency has to be right. This is what I learned making that true.

Two currencies, and only one of them may change

The mistake underneath the step change was having one notion of "the currency" when the system needs two:

  • A storage currency, fixed at the start of the project and never changed. Every snapshot ever written — daily net worth, per-holding valuations — is denominated in it. It is a property of the database, not of the person looking at it.
  • A display currency, chosen at runtime, persisted per user, and changeable at any moment. It affects what is rendered and absolutely nothing that is stored.

When those are the same variable, the snapshot writer follows the dropdown. Switch from one currency to another on a Tuesday and Tuesday's row is written in the new one, sitting in a table where every previous row is in the old one. The chart draws a cliff. Worse, the weekly change report diffs the two rows and reports every position as having moved twenty percent, which is the sort of thing that ruins a morning.

The way I enforced the separation is blunt and has held up: the valuation objects carry mirror fields in the storage currency alongside the display ones — value and value_sgd, cost and cost_sgd, and so on. Anything that persists must use the mirror fields. Anything that renders uses the display fields. The rule is checkable by reading a single line, which matters more than elegance for a rule you need to apply in a dozen places you have not written yet.

The trap: a default argument binds at import

This one cost me an afternoon and is worth the price of the whole post.

the bug
def format_money(amount, currency=config.base_currency()):
    ...

That looks like "default to whatever the current currency is". It is not. Python evaluates default arguments once, when the function is defined — which here means when the module is first imported, which means at process start. The default is frozen to whatever the currency was at boot. Switch currencies and this function keeps answering in the old one, for the life of the process, with no error and no warning.

The symptom is maddening because it is partial. Most of the page updates. One panel does not. Restart the app and the stale panel is now correct and a different one is wrong, depending on import order and what you switched to.

The rule

Never put a value that can change at runtime in a default argument. The signature becomes currency: str | None = None, and the body does currency = currency or config.base_currency(). It is two extra lines and it removes an entire class of bug that produces no stack trace.

The same trap has a second form worth knowing: a module that does from config import BASE_CURRENCY takes a copy of the value at import time. Import the module and read the attribute at call time instead.

Reading history: convert per date, not per series

The other half of the problem is what to do when someone switches currency and looks at three years of history. The obvious implementation converts the finished series by today's rate. It is wrong in an interesting way.

Multiplying an entire series by one constant produces a chart with exactly the same shape as the original, just with different axis labels. Every currency draws an identical picture. Which means the chart is silently telling you that FX did not move — when in fact the FX move is often the most interesting thing that happened to a cross-currency portfolio that year.

The correct version restates each stored point at the rate that applied on that point's own date. In pandas that is an as-of join against a rate series, which handles the fact that FX quotes do not exist on days the market was shut:

converting a stored series
rates = fx.rate_series(STORAGE_CCY, display_ccy, start, end)  # sparse, business days

def convert_series(values: pd.Series, rates: pd.Series) -> pd.Series:
    # For each snapshot date, take the most recent rate at or before it.
    # asof() is the whole point: a weekend snapshot uses Friday's rate,
    # not the next available one, and not a single rate for the whole span.
    aligned = rates.asof(values.index)
    return values * aligned

Now each currency's chart has its own shape, and the difference between them is the FX contribution — which is information, not noise.

When the rate itself is missing

Free FX data is unreliable in a specific way: the usual source returns a stale last close at weekends and after hours, silently. Not an error — a number, just the wrong one. So the FX lookup is a ladder, and each rung is there because the one above it failed in production:

  1. Ask for the currency pair directly.
  2. If that is empty, ask for the inverse pair and reciprocate it.
  3. If that is empty too, fall back to a second, independent provider.
  4. If everything fails, return 1.0 with a staleness flag set, and let the page say so.

The last rung is the one worth arguing about. Returning 1.0 is obviously wrong. But the alternative — raising — takes down a page that is 90% useful for a reason the reader cannot act on. Returning a wrong number silently is the only genuinely unacceptable option. Degrade, but say so.

Threading the currency through without touching thirty call sites

One more piece. Reports are generated, archived as HTML, and read back weeks later. A report must render in the currency it was built in — an archived file that silently restates itself when you change a dropdown is not an archive.

The report builder had around thirty calls to a small _money() formatter, none of which took a currency. Threading a parameter through all of them would have been a large, mechanical, error-prone diff where a single missed call site produces a report with two currencies in it.

A ContextVar solved it in about six lines. The report sets the currency for the duration of its own render; _money() reads it; every call site is untouched. It is the right tool for exactly this shape of problem — an ambient value scoped to one operation — and it is properly isolated across threads and async tasks, which a module-level global is not.

And the one that had nothing to do with currency

While auditing the valuation code I found a worse bug, and it belongs here because it is the same category of mistake: a type that cannot represent "unknown".

When a price provider fails — a delisting, a rate limit, a cold cache — it returned a quote with a price of zero and an "unavailable" flag. The valuation code read the price, ignored the flag, and paired a market value of zero with the holding's real, correct cost basis. Which is a complete loss:

what the table showed
SOMETHING   value 0      cost 20,000    P/L −20,000    −100.0%   ← no quote available

TOTAL       P/L −18,000  return −60%
            (truth, over the holdings that actually had prices: +2,000, +20%)

The fabricated position then topped the chart of biggest contributors to P/L, which is the cruellest possible place for it to appear: the one panel where a large negative number looks like a finding rather than a fault. And it fires exactly when you are least likely to interrogate it — during a rate-limit episode, when several things look odd at once.

The fix is to make the type honest. An unpriced holding has None for value, profit and return — not zero — and the page reports how many rows it could not price rather than folding them into the total.

The part I want to remember

I fixed it, verified the table, and moved on. It came back a week later, because a second code path recomputed cost basis natively from its own inputs and needed the same guard applied separately. One bug, two places, no shared code between them. Fixing the first re-opened nothing; it just failed to close the second. When a bug comes from a convention rather than a function, grep for the convention.

The generalisation is the one I care about most, because it is not a finance problem at all. Missing is not zero. It is the same mistake as imputing 0 for an absent feature and letting a model read it as a real measurement of "none", or treating an uncovered region as evidence of no variant rather than absence of evidence. Zero is a value. Unknown is a different thing, and if your type cannot say so, some downstream average will confidently tell you it was zero all along.
