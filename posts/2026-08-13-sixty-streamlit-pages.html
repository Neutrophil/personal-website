Notes from sixty Streamlit pages

  • Streamlit
  • Learning notes
  • Python

I have built five Streamlit apps over the past year — a portfolio dashboard, a spend tracker, a trading-research rig, a study tracker, a job-search assistant — totalling somewhere north of sixty pages. Streamlit is genuinely excellent for this: a data person gets a usable interface in an afternoon, with no frontend build to maintain.

It also has a specific personality. Its execution model — rerun the entire script, top to bottom, on every interaction — is simple enough to state in one sentence and surprising enough that most of my bugs came from forgetting it. These are the notes I wish I had at the start, roughly in order of how much time each one cost me.

1. A page returns HTTP 200 even when its script raises

This is the one that matters most, so it goes first.

My deployment check was to start the server headless and curl the root URL. Two hundred, ship it. But Streamlit catches an exception in your script and renders the traceback inside the page. The HTTP layer is completely happy. It served a page, the page just happens to be an error message.

So a status code proves the server booted, and nothing whatsoever about whether the app works. What actually catches this is Streamlit's own test harness, which executes a page the way the runtime does and lets you assert on the resulting element tree:

tests/test_pages_smoke.py
@pytest.mark.parametrize("page", ALL_PAGES)
def test_page_renders_without_exception(page, seeded_db, fake_providers):
    at = AppTest.from_file(page, default_timeout=30).run()
    assert not at.exception, f"{page} raised: {at.exception}"

Fourteen pages, one parametrised test, run against a synthetic book with the network faked out. It has caught more regressions than every other test in that project combined, because it exercises the layer where the pieces actually meet.

2. Two traps inside that harness

Patch the provider, not the accessor. I spent an hour convinced the test harness was broken because my fake quote source was being ignored. It was not ignored — the function under test had captured the real one as a default argument at import time, long before the test patched anything. Patching has to happen a layer deeper, on the object the default was captured from, not on the name the test can see.

Switching pages does not replay the entrypoint. The harness's page-switch helper runs the new page but not the router that would normally have set up the sidebar and chrome. So anything the router injects is simply absent from the tree, and an assertion about it fails for reasons that have nothing to do with the page.

3. Once you use st.navigation, the pages folder is invisible

Streamlit has two navigation systems. The old one derives the menu from filenames in a pages/ directory. The new one takes an explicit list of page objects.

They do not compose. Adopt the explicit registry and the folder stops being magic: filenames no longer order anything, and a module that is not named in the registry is simply not part of the app — no menu entry, no error, no hint. I wrote a page, saved it, reloaded, and stared at an unchanged sidebar for a genuinely embarrassing length of time.

There is a sharper edge here. The mere existence of a directory called pages/ next to your entry script can re-enable the legacy behaviour and override your registry on a fresh server start. In the projects that use the explicit registry, the folder is called views/ for exactly this reason. Renaming a directory is a strange bug fix, and it is the correct one.

Two smaller things in the same area: page configuration is a once-per-session call and belongs to the router alone, and the icon you pass for a page must be a real emoji. I used a currency sign that looks like one. It is not one, it is rejected, and the failure takes down the router — which means the whole app, not just that page.

4. Every tab body runs on every rerun

Tabs look like lazy loading. They are not. Streamlit executes the body of every tab on every rerun and then hides all but one with CSS. A tab conceals content; it does not defer computing it.

So the expensive fundamentals fetch that lived in the fourth tab was running on every single interaction, including ones on the first tab. Anything costly behind a tab needs to be either cached or put behind an explicit control that the user has to press.

5. The ten-second click

My favourite one, because the fix was six lines and the measurement was the entire job.

A helper translated instrument codes into display names. It read a lookup table from SQLite and parsed a roughly two-megabyte JSON blob — on every call. On a book of a few hundred holdings, resolving all the names took about three and a half seconds. The home page called it over the whole book three times per rerun.

Which meant every interaction cost around ten seconds. Including — and this is where it stopped being funny — each keystroke in the search box, because typing is an interaction and an interaction is a rerun.

before and after
resolve 336 names, first pass    3.47 s   →   0.031 s
resolve 336 names, second pass  3.46 s   →   0.000 s

The fix is a process-level memo with a short re-check against the database so an edit still shows up, guarded by a lock because it is called from inside a thread pool. Two consequences worth writing down, because both bit me afterwards: the app's "refresh data" button has to reset the memo along with everything else, or it stops being a refresh; and a test fixture has to clear it between tests, or one test's seeded table quietly answers another test's lookup against a different database.

The general lesson is not "add caching". It is that in a framework which reruns everything, the cost of a function is multiplied by a factor you are not thinking about — and the only way to know that factor is to measure the page, not the function.

6. Never pre-format a number you want sorted

I had tables where every numeric column was converted to a formatted string before display — percentages with signs, thousands separators, fixed decimals. It looked right.

It sorted as text. +9.9% ranked above +12.0%, because 9 comes after 1. A Sharpe ratio column could not be meaningfully sorted at all. The whole point of an interactive table is that the reader can reorder it, and the formatting had silently removed that.

The answer is to keep numbers as numbers and describe their presentation through the table's column configuration, so display and ordering come from different things. I had used that configuration mechanism exactly zero times across five apps, which tells you something about how easy it is to miss.

7. Key widgets by identity, never by position

A widget's key is its identity across reruns. Key a text area by its index in a list and you have tied it to a slot, not to the thing in the slot.

Reorder the list — a sort, a filter, a new item at the top — and the widget in slot two is now showing the previous occupant's text. Worse, Streamlit ignores the value you pass once a key exists in session state, so the stale content is sticky. And the next save writes it back under the new occupant's name.

Key by something stable about the item itself.

8. Sidebar ordering is load-bearing

One of the apps has a language toggle. The toggle lives in the sidebar; the sidebar is drawn by the router; the page body is drawn afterwards.

Draw them in the wrong order and switching language leaves the menu and the page title in the previous language for one rerun, because they were rendered before the new setting was read. It corrects itself on the next interaction, which is precisely what makes it hard to catch — it looks like a rendering glitch rather than an ordering bug. Anything that changes how everything else renders has to be resolved first, once per rerun, before anything reads it.

The thread running through all of these

Every one of these is the same misunderstanding wearing a different hat: I wrote code as though it ran once, in a framework that runs it constantly.

The reruns are what make Streamlit pleasant — no state synchronisation, no event handlers, just a script that describes the page. But the model quietly changes what "expensive", "cached", "lazy" and "identity" mean, and nearly every bug above is a place where I used one of those words with its ordinary meaning.

If I were starting a sixth app tomorrow, I would write the smoke test that renders every page before I wrote the second page. It is four lines, and it is the only one of these lessons that finds the others for you.
