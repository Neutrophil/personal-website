I keep a handful of personal projects that read financial documents. At some point I sat down and actually audited what had ended up committed across them, rather than assuming, and the answer was worse than I expected. Nothing catastrophic followed — but there were no technical controls at all, and "I will be careful" is not a control.

So I wrote one. This is the design, which turned out to be more interesting than I expected, because a tool that hunts for secrets has an awkward relationship with the secrets it hunts for.

Rule zero: the scanner must not contain what it detects

The obvious way to catch a specific account number is to search for that account number. Which means writing it into a file, which means committing it, which means the scanner is now the leak. Every improvement to its accuracy makes the problem worse.

So the code carries only generic patterns: shapes, checksums, structural rules — nothing that identifies anyone. The specific values live in a file outside every repository, mode 0600, that is never committed and never will be. The scanner loads it at startup if it is there.

That split has a consequence I did not anticipate, and it is the most important line in the whole tool: if the local file is missing, the scan does not report "clean". It fails. A guard running without its most specific rules and announcing success is more dangerous than no guard at all, because it manufactures confidence. Silence has to mean "I checked", never "I could not check".

Checksums beat regexes

Most of the interesting detection work is in reducing false positives, because a noisy scanner gets ignored and an ignored scanner is decoration.

Payment card numbers are the clean example. The naive rule — thirteen to nineteen digits — matches timestamps, hashes, and half the numbers in a test fixture. Adding the Luhn check helps, but not as much as you would hope: Luhn is a single mod-10 digit, so roughly one in ten random digit strings passes it. Requiring both Luhn and a plausible issuer prefix — the industry ranges are narrow and public — cuts the false positive rate by another order of magnitude, because a random number has to now satisfy two independent constraints.

National identity numbers are similar: the format is a letter, seven digits and a check letter, and the check letter is computed from a weighted sum. Validating it turns a pattern that matches a great many strings into one that essentially only matches real identifiers.

The lookarounds matter too, and in a direction I got wrong first. My instinct was to require a word boundary. But the code I am scanning is a statement parser, and the way it sees a card number is embedded in a run of surrounding text with no whitespace at all. So the exclusions are on adjacent digits only — a longer number is not a card number, but a card number wedged between letters still is.

The rule that needs a hint, and the hole that leaves

Money is much harder than it looks, and the design here is a real trade-off rather than a clean answer.

A monetary amount has no distinguishing structure. It is just a number. The only signal available is a currency marker sitting next to it — so the rule requires one, and requires the value to clear a threshold so that version strings and small constants stay quiet.

Even that needs care. A currency symbol may abut its digits, because that is how it is printed. A three-letter currency code may not, because a filename of the form CCY20260809 is a code followed by a date and not a payment of twenty million. There is a helper whose entire job is to recognise a bare date so it can be excluded, and the suffix form (a number followed by a code) additionally demands thousands separators or decimals before it will fire.

The hole

Because the rule needs a currency marker, a bare 12345.67 sitting in a variable assignment is invisible to it. That is exactly the shape a real figure takes in source code and in documentation — nobody writes the currency symbol in a Python literal. The generic rule cannot close this without flagging every number in every file.

So it is closed from the other side: any figure known to be real goes into the local denylist, where it is matched however it is written. The generic rule catches the shape; the denylist catches the instance. Neither alone is sufficient, and knowing which of your rules is the load-bearing one for a given class of data is worth more than adding a seventh rule.

The output is part of the attack surface

This is the design decision I am most pleased with, and it is the one I would have skipped if I had not thought about where findings actually go.

A scanner prints what it found so you can fix it. Those printed findings land in a terminal, in a scrollback buffer, in a CI log, in a bug report — and, in my case, straight into the context window of an AI coding assistant. An unredacted finding does not report the leak. It performs it, into several new places at once.

So findings are redacted before they are printed, in three passes:

  1. Mask the matched span itself, keeping the first and last couple of characters so a human can still tell which occurrence is being discussed.
  2. Mask every other number remaining on that line. This is the pass I would not have written unprompted. Consider a line listing three balances: the rule fires on the first, and a naive redaction masks that one and publishes the other two, in a message specifically designed to be copied and pasted.
  3. Re-mask anything matching the denylist, regardless of which rule actually fired.

The result is that the tool's output is safe to paste anywhere — which is the property that makes it usable at all. A security tool whose findings you have to handle carefully has moved the problem rather than solved it.

The same reasoning drives the path rules. Data files are identified and blocked by path and extension, and are never opened. A scanner that reads a database to check whether it contains anything sensitive has already loaded it into memory, and possibly into a log line.

Policy per repository, committed on purpose

Every rule has legitimate exceptions, and the exceptions are where a security tool usually rots — someone adds a global suppression to unblock a deadline and it is never revisited.

So exceptions are per-repository, in a committed file, in three explicit forms:

  • A path glob exempting a file from scanning entirely. Reserved for things that are fake by definition — example templates, and the scanner's own test corpus, which by necessity contains a sample of everything it detects.
  • A rule name disabling one rule for that repo. The site you are reading uses this: publishing my name and my email address is the entire point of it, so the rules that would flag them are switched off here and nowhere else.
  • A promotion, turning an advisory rule into a blocking one where a repo wants to be stricter than the default.

Keeping it per-repository means one project's exception cannot silently widen another's, and keeping it committed means every deviation shows up in a diff with a comment explaining itself. That combination is what makes exceptions survivable.

Four gates, and one lesson about where they attach

The layers are ordinary. What I got wrong, and would get wrong again, is where the hooks attach.

The first version installed hooks into each repository and scoped them to my workspace directory. It looked complete. Then I cloned one of those repos somewhere else to test something, and a probe commit carrying a deliberately planted card number went straight through — no hooks in the fresh clone, and the path check would have failed anyway.

Git does not track .git/hooks. A per-repo install is therefore not a property of the project; it is a property of one checkout on one machine, and it evaporates the moment anyone clones. The fix was to set a global hooks path so every repository on the machine — including ones that do not exist yet — is covered, and to decide whether to guard based on either the workspace path or the origin URL. The guard follows the repository, not the directory. Third-party clones stay unguarded deliberately, because their own fixtures would block their legitimate commits.

The weekly audit exists for the same reason. It re-scans everything, but its more useful job is answering "are the hooks still there?" — because the failure mode of a protection layer is not usually that it breaks loudly. It is that it quietly stops being installed and nobody notices for months.

What it does not do

Two honest limits, both documented rather than hidden.

It can be bypassed. Git has a flag to skip hooks, and the tool honours an environment variable that disables it. Both are deliberate. This is a guard against accidents, not against a determined operator — and a tool with no escape hatch gets uninstalled the first time it blocks something urgent and legitimate. What I did instead was make bypassing loud: any use of either is treated as an incident worth writing down.

Some exposure is structural. A tool that fetches market data discloses which instruments it asks about, and the set of instruments is itself informative. No amount of scanning fixes that. It goes in the risk register as accepted, which is a more useful place for it than in the back of my mind.

The last piece is egress rather than commits: anything leaving the machine for a third-party API is relativised and pseudonymised first — shares of a total instead of absolute figures, opaque labels instead of real names. That works because the analysis I actually want is scale-invariant. Concentration, allocation and overlap are all questions about proportions, so the answers are unchanged and the magnitudes stay home. The check runs over the fully assembled payload rather than its parts, and if the checker cannot even be imported it refuses to send. Fail closed, or do not bother.
